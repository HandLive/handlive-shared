# Cross-platform test vectors (Kotlin ↔ Swift ↔ Rust)

Specification: `docs/detailed-design/00-common-specs.md` (0.2, 0.3, 0.4.1, 0.5, 0.6), `02-pairing.md` (PAIR-01, PAIR-02) and `03-connectivity.md` (CONN-01). The files are generated by `tools/vectors/generate_vectors.py` — **never edit them by hand** — and checked by `tools/vectors/verify_vectors.py`. Every key is a public test value (an RFC key or `SHA-256("HL-TEST|<label>|<i>")`), never a real key.

## Common conventions

- Each file: `{"description", "source", "vectors": [...], "invalid_vectors": [...]?}`. Each vector has a `name` (unique in its file). Every file has at least 2 vectors.
- `vectors`: every field must be reproduced exactly. `invalid_vectors` (negative vectors): the AEAD, MAC or signature check **must fail**; the `reason` field is one of `tag_mismatch`, `aad_mismatch`, `ciphertext_mismatch`, `payload_too_short`, `mac_mismatch`, `message_tampered`, `signature_mismatch`, `wrong_key`, `wrong_label`, `device_id_mismatch`, `signature_length`, `signature_not_canonical`, `key_mismatch`, `wrong_byte_order`, `wrong_encoding`, `wrong_field_order`, `wrong_pin`, `wrong_parameters`, `hint_outside_window`. In `pair-handshake.json` and `discovery-hint.json` a negative vector also names the check that must fail and the evidence of the mistake (see those files).
- Bytes: lowercase hex without prefix. Integers: JSON numbers. Display/UTF-8 strings: JSON strings.
- Wire strings keep the form of the spec (0.3): an envelope's `payload` is **b64** (RFC 4648 §4, with padding); `eph`, `nonce`, `mac` inside JSON are **b64u** (RFC 4648 §5, no padding); uuids are 36 lowercase characters.
- JSON strings (plaintext, envelope) are compact (no whitespace), keep their key order, and are UTF-8 without escapes. Encryption must use **exactly the bytes** of the string in the vector; a receiver parses the JSON instead of comparing strings.
- `direction`: `c2s` = Mac/iOS → Android (key `k_c2s`), `s2c` = Android → Mac/iOS (`k_s2c`). `key_source` names the vector a key comes from (to chain tests); the `key` field always holds the full value.
- HKDF = HKDF-SHA256. When the spec gives no salt → **empty salt** (≡ 32 zero bytes).

## Interpretations settled where the spec is not explicit

| Point | Choice | Reason |
|-------|--------|--------|
| `T1`, `T2` (0.6.3) | Concatenate **raw bytes**: `"HL1|hello|"` (ASCII) ‖ `pair_id` 16 bytes ‖ `device_id`C 16 bytes ‖ `eph`C 32 bytes ‖ `nonce`C 32 bytes (= 106 bytes). `T2` = `"HL1|welcome|"` ‖ `T1` ‖ `device_id`S 16 ‖ `eph`S 32 ‖ `nonce`S 32 (= 198 bytes). Not the 36-character or b64u forms | Like `T_offer` in 02-pairing (fixed-length byte fields) |
| MAC `HLSTREAM1` (0.6.3 step 7) | `"HLSTREAM1|"` ‖ `session_id` 16 bytes ‖ `nonce_c` 32 bytes; welcome: `"HLSTREAM1|welcome|"` ‖ `session_id` 16 ‖ `nonce_c` 32 ‖ `nonce_s` 32 | Same as above |
| `info` of `K_stream` | UTF-8 string `"handlive/v1/stream/<channel>/<session_id, 36 characters>"`, `<channel>` = the path segment: `camera`, `call-audio` | `info` is text; 07-call-audio writes exactly this form |
| `K_auth` | HKDF(ikm = `PRK`, empty salt, info `"handlive/v1/session-auth"`, L = 32) | The spec gives neither salt nor L |
| Salt of `PRK` | Compare `device_id`s as 16 bytes in unsigned byte order (= comparing the lowercase uuid strings) | |
| Rekey | `X25519(initiator eph, responder eph)`; ikm = shared ‖ old `secret` (64 bytes); salt = SHA-256(initiator `nonce` ‖ responder `nonce`); `k_c2s` = first 32 bytes, `k_s2c` = last 32 bytes by the C/S roles (not by who initiated); the 64-byte result replaces `secret` for the next rekey. `epoch` is not part of the KDF | The spec says "the two nonces" without an order |
| `K_stream` | Derived from the `secret` of the handshake (epoch 0) in the vector | The spec does not say which `secret` to use after a rekey |
| MAC input of `pair/confirm` (PAIR-01 API 4) | The confirm label, then `T_offer` ‖ `pair_id` 16 bytes ‖ `created_at` int64 BE ‖ `sig` 64 raw bytes (not the b64u text); every pairing label is ASCII without spaces (listed under `pair-handshake.json`) | As in the attestation (0.6.2); JSON is never MACed |
| `str(x)` in `T_offer` | uint16 BE byte count ‖ the UTF-8 bytes of the string exactly as sent in JSON, **no Unicode normalization** (`QR cặp 2` has an NFD phone name) | The spec does not mention normalization; Android and Apple hash what is on the wire |
| `K_pin` (0.6.2) | Argon2id version 0x13, password = UTF-8 of the 6 digit characters (leading zeros kept, never an integer), salt = `nonce_c` ‖ `nonce_s` (64 bytes), no secret and no associated data | The spec gives the parameters but not the password encoding or the version; the choice of the Android and Apple code |
| QR URI (PAIR-01 API 1) | Generator form: parameters in the order `v`, `pk`, `ps`, `d`, `rv`; `d` percent-encodes every UTF-8 byte outside the RFC 3986 unreserved set as uppercase `%XX` (space = `%20`, `&` = `%26`). A receiver parses the URI instead of comparing strings | The spec gives only an example |
| Discovery hint (0.4.1) | Hour = `floor(now_ms / 3 600 000)` (rounded down, negative values too; the previous hour of hour 0 is −1, int64 two's complement); hint = lowercase hex; TXT `h` joins hints with `,` without spaces; the client accepts the current hour, then the previous one, by its own clock | `floor` and the byte form are in the spec; case, separator and order are not |
| Negative vectors of `pair-handshake.json` | `check` is the **first** check that fails in the receiver's order from the spec: API 2 rule 2 then 3 (`hello_key`, `hello_device_id`); API 3 rule 3 (`offer_mac` → `offer_device_id` → `offer_tls`); API 4 rules 1–2 and API 5 rule 1 (MAC → `prk_check` → signature) | A wrong value must be caught by the check it targets, not by an earlier one |

## Files

### `xchacha20-poly1305.json`
AEAD_XChaCha20_Poly1305. `key` 32, `nonce` 24, `aad`, `plaintext`, `ciphertext` (same length as the plaintext), `tag` 16. Extra fields for Apple: `hchacha20_subkey` = HChaCha20(key, nonce[0:16]); `chacha20_nonce` = `00000000` ‖ nonce[16:24]; ChaCha20-Poly1305(subkey, chacha20_nonce) must give exactly ciphertext ‖ tag. Vector 1 = draft-irtf-cfrg-xchacha-03 §A.3.1; the others are generated with libsodium. `invalid_vectors`: same fields, without `plaintext`.

### `hchacha20.json`
`key` 32, `nonce` 16, `subkey` 32. Vector 1 = draft §2.2.1; vector 2 = the input of §A.3.1 (subkey computed here, checked with libsodium); vector 3 generated.

### `chacha20-poly1305.json`
AEAD_ChaCha20_Poly1305 with a 12-byte nonce (CryptoKit `ChaChaPoly`). RFC 8439 §2.8.2 (`nonce` = fixed-common `07000000` ‖ IV) and §A.5. Fields as for XChaCha.

### `x25519.json`
`scalar` 32 (not clamped; the function clamps), `u` 32, `output` 32. RFC 7748 §5.2 (2 vectors) and §6.1 (Alice's and Bob's public keys with `u` = 9, the shared secret K from both sides).

### `hkdf-sha256.json`
`ikm`, `salt` (empty = `""`), `info`, `length` (bytes), `prk` (extract), `okm`. RFC 5869 A.1–A.3.

### `device-id.json`
`ik_sig_seed` (Ed25519 secret key, 32 bytes, RFC 8032 §7.1 TEST 1–3), `ik_sig_pub`, `sha256` = SHA-256(pub), `device_id_bytes` = the first 16 bytes after setting byte 6 = `(b & 0x0f) | 0x80` and byte 8 = `(b & 0x3f) | 0x80`, `device_id` = the uuid form.

### `ed25519.json`
`seed` (32-byte secret key), `public_key`, `message`, `signature` (64 bytes R ‖ S): RFC 8032 §7.1 TEST 1–3, the same keys as `device-id.json`. Ed25519 is deterministic: signing `message` again with `seed` must give exactly `signature`. Same algorithm as the attestation signature (PAIR-01) and the signatures sent to the relay (`relay-auth.json`). `invalid_vectors`: `{public_key, message, signature, reason}`, the check must fail — tampered message (`message_tampered`), R or S tampered (`signature_mismatch`), another key (`wrong_key`), S replaced by S + L (`signature_not_canonical`: a lax verifier accepts it; RFC 8032 §5.1.7 requires S < L), a 63-byte signature (`signature_length`).

### `relay-auth.json`
`kind` = `register` (`POST /v1/devices`, CONN-03 API 1) or `auth` (`POST /v1/auth/token`, 0.6.4, CONN-03 API 3). Common fields: `ik_sig_seed`, `ik_sig_pub` (the RFC 8032 TEST 1–3 keys), `device_id` (as in `device-id.json`), `message`, `sig` (hex), `request` (the JSON body on the wire, compact, b64u without padding). `register` adds `platform` (`macos`, `android`, `ios`), `app_version`, `ts`; `message` = `"HLREG1"` ‖ device_id 16 bytes ‖ ik_sig_pub 32 ‖ UTF-8(platform) ‖ ts int64 BE. `auth` adds `challenge` (32 bytes) and `challenge_b64u`; `message` = `"HLAUTH1"` ‖ challenge ‖ device_id 16. `invalid_vectors`: `{kind, reason, ik_sig_pub, request}` (`auth` adds `challenge` = the value the relay issued; `ik_sig_pub` is the key the relay stores for `device_id`), which the relay must reject: `message_tampered` (ts, platform or challenge changed after signing; `signed_message` is the message actually signed), `device_id_mismatch` (a correct signature, but `device_id` is not derived from the key), `wrong_label` (signed with the other label), `wrong_key` (`signer_pub` is the key that signed), `signature_length` (400 `BAD_REQUEST`), `signature_not_canonical` (S + L); except for `signature_length`, the relay answers 401 `SIGNATURE_INVALID`.

### `pair-prk.json`
Two pairs, one where the client's `device_id` is the smaller and one where it is the larger (`client_id_is_smaller`). `ik_dh` = the Alice/Bob keys of RFC 7748 §6.1. `dh_shared` = X25519(own ik_dh, peer ik_dh) (the same on both sides); `ikm` = `dh_shared` ‖ `pairing_secret` (64 bytes); `salt_input` = smaller id ‖ larger id (32 bytes); `salt` = SHA-256(salt_input); `info` (UTF-8 string), `length` = 32; `prk`.

### `pair-handshake.json`
The whole PAIR-01 exchange (API 1–5 and the body of API 8) and the PAIR-02 Security Code, chained from `pair-prk.json` by `keys_from`. Labels (ASCII, no spaces): `HL1|offer|`, `HL1|confirm|`, `HL1|done|`, `HL1|prk-check-c|`, `HL1|prk-check-s|`, `HLPAIR1`. `QR cặp 1` and `QR cặp 2` are pairs 1 and 2 of `pair-prk.json` exactly (same keys, `pairing_secret` and `pair_id`, so `prk` is the `pair-prk.json` value; the client's `device_id` is the smaller in one and the larger in the other); `PIN cặp 3` uses the keys of pair 1 with a new `pair_id` and `K_pin` instead of `pairing_secret`. Fields:
- Identities: `client_*` and `android_*` = `ik_sig_seed`, `ik_sig_pub`, `device_id`, `ik_dh_priv`, `ik_dh_pub` (the RFC keys of `device-id.json` and `pair-prk.json`), `client_name`, `client_platform`, `client_model`, `android_name`, `android_model`, `android_os_version`; `tls_sha256` = 32 bytes standing for SHA-256 of A-SVC's certificate (DER), the value the client pins and sees on the LAN connection.
- QR (`mode` = `qr`; null in PIN mode): `qr_uri` (≤ 300 characters; `QR cặp 2` has `rv` and a name with `&`), `qr_pk`, `qr_ps` (b64u as in the URI), `qr_rv` (hex or null), `pr` = TXT `pr` = the first 8 lowercase hex digits of SHA-256 over the 32 decoded bytes of `pk`, `pairing_secret`.
- PIN (`mode` = `pin`; null in QR mode): `pin` (6 digits with a leading zero), `argon2` = `{variant, version (19 = 0x13), t, m_kib, p, length}` of 0.6.2, `k_pin`.
- `nonce_c`, `nonce_s`; `secret` = `pairing_secret` or `k_pin`; `k_pa_salt` (= `nonce_c` ‖ `nonce_s`), `k_pa_info`, `k_pa`.
- `t_offer` and `t_offer_parts` (`[{field, hex}]` in byte order: `label`, `device_id_c`, `nonce_c`, `ik_sig_pub_c`, `ik_dh_pub_c`, `name_c`, `device_id_s`, `nonce_s`, `ik_sig_pub_s`, `ik_dh_pub_s`, `tls_sha256`, `name_s`; each `name_*` is the whole `str()`), `offer_mac`.
- `created_at`; `attestation` (127 bytes) and `attestation_parts`; `sig_c`, `sig_s` = Ed25519 of the client and of Android over the attestation (deterministic: signing again must give the same bytes); `security_code` = the first 8 lowercase hex digits of SHA-256(`attestation`), identical on both devices.
- `confirm_mac_input` and its parts (`label`, `t_offer`, `pair_id`, `created_at`, `sig`), `confirm_mac`; `done_mac_input` and its parts (`label`, `pair_id`, `sig`), `done_mac`.
- `dh_shared`, `prk_ikm`, `prk_salt_input`, `prk_salt`, `prk_info`, `prk`; `prk_check_c_input`, `prk_check_c`, `prk_check_s_input`, `prk_check_s`.
- `hello_plaintext`, `offer_plaintext`, `confirm_plaintext`, `done_plaintext` (JSON `{op, data}`, keys in the order of the spec tables, keys, nonces, MACs and signatures as b64u) and the matching `…_envelope` (`type` = `pair`, `payload` = b64 of the plaintext, not encrypted; the UUIDv7 `id` carries `ts` in its first 48 bits). Feeding `hello_envelope` and `confirm_envelope` to Android with its identity, `nonce_s` and `tls_sha256` must produce exactly `offer_plaintext` and `done_plaintext` (apart from the envelope `id`/`ts`).
- `pairs_request`: the body of `POST /v1/pairs` (API 8): `device_a` = Android, `device_b` = the client, `attestation` as b64u, `sig_a` = `sig_s`, `sig_b` = `sig_c`.

`invalid_vectors`: `{name, vector, message, check, checked_by, reason, expected_error}`, plus `plaintext` and `envelope` when `message` is set (that message with the wrong value; every other input comes from the positive vector named by `vector`), plus the evidence of the mistake. `check` is the first check that fails (see the table above): `hello_key`, `hello_device_id` (Android), `offer_mac` (client), `confirm_mac`, `prk_check_c`, `sig_c` (Android), `done_mac`, `prk_check_s`, `sig_s` (client), `k_pin`, `pr` (`message` = null, both sides). `checked_by` = `android`, `client` or `both`. `expected_error` = the `pair/error` code: `AUTH_FAILED`, `PIN_INVALID` for a wrong offer MAC in PIN mode (A5) and for a wrong `K_pin`, null for `pr` (the phone is simply not found, E3). Reasons and their evidence:
- `mac_mismatch`, `signature_mismatch`: one bit flipped; for a signature the MAC is recomputed over the tampered signature, so only the signature check fails.
- `wrong_label`: the label copied with spaces from the Markdown `\|` (`"HL1 | offer | "`, `confirm`, `done`; `mac_input`) or the other side's `prk-check` label (`prk_check_input`).
- `wrong_byte_order`: little-endian `str()` lengths (`mac_input`) or `created_at` in the confirm MAC (`mac_input`) or in the signed attestation (`signed_message`); `K_pa` salt `nonce_s ‖ nonce_c` (`mac_key`); `PRK` salt = larger ‖ smaller `device_id` (`prk_salt_input_used`, `prk_used`).
- `wrong_encoding`: `sig` as its b64u text or `pair_id` as its 36-character text in the confirm MAC (`mac_input`); the PIN turned into an integer, losing the leading zero (`pin_used`, `k_pin_used`); `pr` over the b64u text of `pk` (`pr_input`).
- `wrong_field_order`: attestation signed with the client's `device_id` and key before Android's (`signed_message`).
- `signature_not_canonical`: S replaced by S + L (MAC recomputed).
- `message_tampered`: `tls_sha256` replaced in transit (MITM) with the MAC unchanged; `mac_input` = the original `T_offer`.
- `wrong_pin`: Android derived `K_pin` from a mistyped PIN (`pin_used`, `k_pin_used`, `mac_key`); the client's answer is `client_reply_plaintext`/`client_reply_envelope` (`PIN_INVALID`, `attempts_left` = 2).
- `wrong_parameters`: `K_pin` with p = 1 (`argon2_used`, `k_pin_used`) — libsodium's `crypto_pwhash` cannot compute this KDF (it fixes p = 1 and a 16-byte salt).
- `key_mismatch`: `ik_dh_pub` differs from the scanned `pk`; `device_id_mismatch`: `device_id` not derived from `ik_sig_pub`.

### `discovery-hint.json`
TXT `h` hints (0.4.1, CONN-01 step 3 and API 1–2) from the `prk` of `pair-prk.json`. `kind` = `key` (one per pair of `pair-prk.json`): `pair_id`, `prk_source`, `prk`, `info`, `length`, `k_disc`; `hours` = `[{hour, message, mac, hint}]` with `message` = `"HLDISC1"` ‖ hour int64 BE, for hours −1, 0, 1, 479762, 479763, 479764; `clock` = `[{now_ms, hour, advertised, accepted}]`: the hour, the hint the phone advertises and the hints a client at that time accepts (`[current, previous]`), at 0, 3 599 999, 3 600 000, 1 727 150 000 123, 1 727 150 399 999 and 1 727 150 400 000. `kind` = `match`: a phone with the pairs `phone_pairs` advertises `txt_h` (in that order) at `phone_now_ms` (`phone_hour`); a client of `client_pair` at `client_now_ms` (`client_hour`) accepts `accepted` and must find `matched_hint` (`matched_as` = `current`, or `previous` when the phone's clock is behind across the hour boundary). `invalid_vectors`: `{name, pair, reason, client_now_ms, client_hour, txt_h}` plus evidence; the client must **not** treat `txt_h` as a match: `hint_outside_window` (`phone_now_ms`, `phone_hour`: the phone's clock is ahead across the hour boundary, or two hours behind — 0.4.1 accepts only the current and the previous hour), `wrong_byte_order` (hour as int64 LE), `wrong_encoding` (hour as int32 BE), `wrong_label` (`"HLDISC1|"`), `wrong_key` (HMAC keyed with `PRK` instead of `K_disc`, `mac_key`); `message` = the bytes that were MACed.

### `session-handshake.json`
Chained from `pair-prk.json` by `pair_id`. `k_auth`; `client_eph_priv/pub`, `client_nonce` (32); `t1`, `hello_mac` = HMAC-SHA256(k_auth, t1); `server_eph_*`, `server_nonce`, `t2`, `welcome_mac`; `eph_shared` = X25519(eph C, eph S); `secret_salt` = SHA-256(t2); `secret` (64) = HKDF(eph_shared ‖ prk, secret_salt, `"handlive/v1/session"`, 64); `k_c2s` = secret[0:32], `k_s2c` = secret[32:64]. `hello_plaintext`/`welcome_plaintext`: JSON `{op, data}` with `eph`/`nonce`/`mac` as b64u; `hello_envelope`/`welcome_envelope`: envelope `type = session`, `payload` = b64 of the plaintext (not encrypted). `invalid_vectors`: `{key, message, mac}` — HMAC(key, message) compared in constant time with `mac` must **differ**.

### `session-rekey.json`
Epoch 1 (the client initiates, `secret_old` = the handshake `secret` of pair 1) and epoch 2 (the server initiates, `secret_old` = `secret_new` of epoch 1). `initiator_*`/`responder_*` (eph priv/pub, nonce), `eph_shared`, `ikm` (96 bytes), `salt_input` (64 bytes), `salt`, `info`, `length` = 64, `secret_new`, `k_c2s`, `k_s2c`. `request_plaintext` = the plaintext of `session/rekey`; `ack_data` = the `data` of the `ack` (responder).

### `stream-keys.json`
Channel `camera` (from the handshake of pair 1) and `call-audio` (pair 2). `secret`, `info`, `length` = 96, `k_stream` = `k_auth`(32) ‖ `k_c2s`(32) ‖ `k_s2c`(32); `nonce_c`, `nonce_s` (32); `hello_message`/`hello_mac`, `welcome_message`/`welcome_mac`; envelopes `stream_hello`/`stream_welcome` (`envelope_type` = `camera` or `call_audio`, payload not encrypted). `invalid_vectors` as in the handshake file (including the two nonces swapped).

### `envelope.json`
`encrypted` = true: `key`, `v`, `type`, `id`, `ts`, `aad` (the string `"<v>|<type>|<id>|<ts>"`), `aad_hex`, `plaintext` (JSON), `nonce` 24, `ciphertext`, `tag` 16, `payload_b64` = b64(nonce ‖ ciphertext ‖ tag), `envelope` (the wire string). `encrypted` = false (handshake messages): `key`/`aad`/`nonce`/`ciphertext`/`tag` = null, `payload_b64` = b64(UTF-8 of `plaintext`). `invalid_vectors`: `{key, envelope}` — the receiver builds the AAD from the envelope's own fields and decrypts, which must fail (wrong tag, `ts`/`type` tampered, payload under 40 bytes).

### `ack.json`
Like an encrypted envelope, `type = ack`, plus `re`, `ok`. Contains an ok ack with `data`, an ok ack with empty `data`, and an error ack `SMS_NO_SERVICE` (`error.code`, `message`, `details`).

### `clipboard-chunk.json`
Like an encrypted envelope but with a binary plaintext: `plaintext_hex` = `hdr_len` (uint16 BE) ‖ `header_json` (UTF-8) ‖ `chunk_data`. Adds `transfer_id`, `index`, `header_json`, `hdr_len` (bytes of the JSON), `chunk_data`. The first plaintext byte is `0x00`. Chunks in the vectors are shorter than `CHUNK_SIZE` to keep them small.

### `hl-frame.json`
`channel`, `direction`, `key`, `seq`, `ts` (uint32), `header` (11 bytes = `484c01` ‖ seq BE ‖ ts BE = the AAD), `plaintext`, `nonce`, `ciphertext`, `tag`, `encrypted_part` = nonce ‖ ciphertext ‖ tag, `frame` = header ‖ encrypted_part. The camera channel adds `track`, `flags`, `pts_us` (int64 BE), `data` (plaintext = track ‖ flags ‖ pts_us ‖ data). One vector uses `seq` = `ts` = 2³²−1 to test the bounds. `invalid_vectors`: `{key, frame}` — `seq` tampered (wrong AAD), wrong tag.

### `envelope-roundtrip.json` (cross-platform, written by Android)
Envelopes encrypted by Android (`android/core/crypto`, Tink XChaCha20-Poly1305) with the fixed keys of `envelope.json` (`k_c2s`/`k_s2c` of pair 1), a UUIDv7 `id` and a fresh random nonce. **Same fields as the `encrypted = true` vectors of `envelope.json`** (`name`, `encrypted`, `direction`, `key`, `key_source`, `v`, `type`, `id`, `ts`, `aad`, `aad_hex`, `plaintext`, `nonce`, `ciphertext`, `tag`, `payload_b64`, `envelope`). Not generated by `tools/vectors/`: it is rewritten only by `cd android && HL_WRITE_ROUNDTRIP=1 ./gradlew :core:crypto:test`; normal test runs only read and decrypt it. Apple (M0.1) decrypts each `envelope` with `key` and compares with `plaintext`. The other way round, the Android tests decrypt `envelope-roundtrip-apple.json` when it exists.

### `envelope-roundtrip-apple.json` (cross-platform, written by Apple)
Envelopes encrypted by Apple (`apple/Packages/HLCrypto`: in-house HChaCha20 + CryptoKit `ChaChaPoly`) with the fixed keys of `envelope.json` (`k_c2s`/`k_s2c` of pair 1), a UUIDv7 `id` and a fresh random nonce; the plaintexts are the exact bytes of the `encrypted = true` vectors of `envelope.json`. Same fields and field order as `envelope-roundtrip.json`. Not generated by `tools/vectors/`: it is rewritten only by `cd apple/Packages/HLCrypto && HL_WRITE_ROUNDTRIP=1 swift test` (add `HL_SWIFT_TESTING_PACKAGE=1` on a machine with only the Command Line Tools); normal test runs only read and decrypt it. Android (A0.1) and the relay decrypt each `envelope` with `key` and compare with `plaintext`.

## Use in CI

Each platform reads these files directly in its unit tests: it recomputes every field of `vectors` and checks that every `invalid_vectors` entry is rejected. On Apple, `xchacha20-poly1305.json` must pass with the in-house HChaCha20 + `ChaChaPoly`.
